- ПОЗЖЕ ПРИЗНАК СФОРМУЛИРОВАН ТОЧНЕЕ: сущность остаётся в boot, если её НЕЛЬЗЯ ВЫЧИСЛИТЬ,

- [stated] ВАЖНАЯ ПОПРАВКА ПОЛЬЗОВАТЕЛЯ: реестр для MET/VIEWS — чисто модульное
  устройство, исходник ни при чём. Он прав: MET и VIEWS суть конструкция РАЗБИВКИ, в

## ПЯТЬ ПРАВОК split.mjs, ПО ПОРЯДКУ
1. **initRefs не спускается в тела вложенных функций.** Ссылка внутри замыкания при
   инициализации НЕ ЧИТАЕТСЯ. Прежняя проверка уводила в boot таблицы из одних ленивых
   замыканий: metricDescriptions 456 строк, FilterModes 171, LoadingIndicator 57,
   PROFILE_METRICS 21 (у последней автор САМ написал `() =>`, чтобы отложить).
   METRIC_COVERAGE_FN откладывается по-прежнему: там ссылки ПРЯМЫЕ
2. **Литеральное значение ячейки S кладётся в модуль-владелец.** До этого приписка
   ячейки к модулю не давала файла вовсе
3. **document и window убраны из ENV.** Модульный скрипт откладывается по стандарту и
   стоит перед </body> — разметка при вычислении тел УЖЕ ЕСТЬ. Осторожность унаследована
   от одностраничной версии, где скрипт исполнялся посреди документа
4. **d3 переведён в ввоз.** Разбивка пишет обёртку vendor/d3.js над UMD-сборкой
   (`import './d3.min.js'; export default globalThis.d3;`) и добавляет `import d3` в
   каждый модуль, где имя упомянуто; классический <script src> убран. ENV ОПУСТЕЛ
5. **База ввозится статически.** core/ns.js делает `import … with { type: 'json' }` по
   шести файлам и собирает DATA до исполнения любого тела; loadData() возвращает готовый
   DATA, асинхронности в запуске нет
6. **Указатели строятся телом graph-index.js.** buildIndexes() зовётся в конце тела; из
   boot повторный вызов УБРАН (второй прогон создаёт НОВЫЕ объекты, и взявший ссылку на
   прежние разошёлся бы с остальными — тихая отложенная поломка, ловит только обход);
   модулю, читающему DATA.<указатель> при вычислении тела, приписывается
   `import './core/graph-index.js';` БЕЗ ИМЁН — ввоз ради ПОРЯДКА
7. **Признак «разрешимо» вместо «литерал».** Значение уезжает домой, если всё, на что оно
   ссылается, готово к вычислению тела (встроенное, окружение, d3, сырая база,
   производные указатели). НЕ ГОТОВЫ ТОЛЬКО ДРУГИЕ ЯЧЕЙКИ — порядок между чужими телами
   ничем не обещан, потому spacingX = viewWidth/(cols+1) ждёт сборки

8. **Разрешимость до неподвижной точки.** Список готового расширен двумя пунктами:
   ОБЫЧНЫЕ СУЩНОСТИ ЧУЖИХ МОДУЛЕЙ (их приносит ввоз, а ввоз обещает порядок — снимает
   currentChronologyMode со ссылкой на CHRONOLOGY_MODES) и ДРУГИЕ РАЗРЕШИМЫЕ ЯЧЕЙКИ, если
   поставить ввоз к их модулю ради порядка. Второе и есть неподвижная точка:
   spacingX = viewWidth/(cols+1) разрешимо ровно постольку, поскольку разрешимо viewWidth.
   ДОМА ЯЧЕЕК СЧИТАЮТСЯ ДО ВЫПУСКА, а не по ходу: иначе ячейка, выпущенная раньше той, на
   которую ссылается, осталась бы без ввоза. Осторожно: homeOf объявлен НИЖЕ этого места,
   брать надо moduleOf

9. **Присваивание к window на верхнем уровне — ОБЪЯВЛЕНИЕ.** В едином файле
   `window.graphSelectionContext = {…}` заводит имя не хуже, чем `let x = {…}`. Пока
   разбор видел безымянный оператор, первое правило уводило его в boot: у имени не было
   дома. ПРАВКУ ПРИШЛОСЬ ВНЕСТИ ДВАЖДЫ — map_globals.mjs и split.mjs разбирают исходник
   КАЖДЫЙ САМ ПО СЕБЕ, карта не питает разбивку. Внесённая только в карту, правка не
   изменила сборку ни на строку. Заслон сработал: remap.mjs проверить показал «сущность
   без модуля», сборка встала до назначения дома (вписал в assign_names вручную —
   remap.mjs перенести не берёт имя, которого ещё нет в раскладке)

10. **Имена пространств MET/VIEWS тоже разрешимы** при ввозе ради порядка — это увело
   домой METRIC_COVERAGE_FN, ПОСЛЕДНЕЕ значение. ОПАСЕНИЕ ПРО ПОДМЕНУ МЕТРИК НЕ
   ПОДТВЕРДИЛОСЬ: installMetricScopeWrappers() ставит обёртки ПРИ ОТКРЫТИИ ОКНА
   СТАТИСТИКИ, то есть много позже сборки; таблица захватывает необёрнутые метрики в
   любом случае — что из boot, что из тела модуля. Вопрос был не в подмене, а ТОЛЬКО в
   порядке. MET остался изменяемым объектом, исходник и модули не тронуты

## ЧТО ЭТО НЕ МЕНЯЕТ (ответ на вопрос пользователя)
Обновление вида при правке НЕ ЗАТРОНУТО: правка меняет DATA в памяти и зовёт
afterDataChange; откуда база взялась при запуске, к этому отношения не имеет. Пропала
лишь возможность перечитать .json с диска в ходе работы — ею никто не пользовался,
loadData() звалась только из сборки. Оговорки: `with { type: 'json' }` — вещь свежая,
ограничение по браузерам; по file:// не работает (модули там и так не грузятся).

## ЦЕЛЬ И ОСТАТОК
Цель — не пустой boot, а BOOT БЕЗ ЕДИНОГО ЗНАЧЕНИЯ. Тогда можно завести утверждение «в
boot нет ни одного присваивания ячейке», и всякое новое отложение будет ловить приёмка,
а не глаз. До этого осталось: реестр MET/VIEWS (упрётся в installMetricScopeWrappers,
который ПОДМЕНЯЕТ метрики на лету — ЕДИНСТВЕННОЕ место, требующее правки исходника);
порядок между телами для spacingX/spacingY; два мелких огрубления признака.

СКРЫТАЯ ЦЕНА boot.js, о которой помнить: его содержимого НЕТ в assign_names.json (там
имена, а boot — безымянные операторы), значит remap.mjs над ним не властен, layers.mjs
держит его верхним слоем по определению, карта дерева видит один узел.
